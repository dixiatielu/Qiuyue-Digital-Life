# Context token budgets and compaction: review

Reviewed: 2026-10-28. This is a record of design research at the time. The subsequent implementation uses server usage plus incremental estimates without a tokenizer; see the README for current configuration and behavior. First-party implementation facts are distinguished from this project’s engineering recommendations. Online documentation may change with versions; key source links are pinned to commits. [README](../../README.md).

## OpenClaw: separate token usage, working-context compaction, and memory persistence

Source commit reviewed: `d1cda17dde7fbd744d812cf7da80ee5aa20b03eb`. The core compaction code prefers valid provider usage to represent the existing context and estimates messages added afterward; a new window cannot reuse pre-compaction usage. It estimates the entire window only when no usage is available. Fallback text estimates include CJK weighting, while images still have a fixed budget. Managing in tokens therefore does not imply an exact tokenizer is used for every complete request. [Reference 1](https://github.com/openclaw/openclaw/blob/d1cda17dde7fbd744d812cf7da80ee5aa20b03eb/packages/agent-core/src/harness/compaction/compaction.ts), [Reference 2](https://github.com/openclaw/openclaw/blob/d1cda17dde7fbd744d812cf7da80ee5aa20b03eb/packages/normalization-core/src/cjk-chars.ts), [Reference 3](https://github.com/openclaw/openclaw/blob/d1cda17dde7fbd744d812cf7da80ee5aa20b03eb/packages/agent-core/src/harness/compaction/compaction-cut-point.ts).

The full request budget includes fixed system instructions, tool schemas, pending input, queued context, and output/compaction reserves. The documented embedded runtime defaults to a 20,000-token reserve capped at one quarter of the active window; manual compaction defaults to a 20,000-token recent-tail target. The underlying packages have different defaults and should not be conflated into one universal configuration. The principle is “window minus reserve,” not unconditional application of fixed 85%/60% ratios. [Reference 1](https://github.com/openclaw/openclaw/blob/d1cda17dde7fbd744d812cf7da80ee5aa20b03eb/src/agents/sessions/compaction/request-budget.ts), [Reference 2](https://docs.openclaw.ai/reference/session-management-compaction/compaction).

Compaction summarizes older exchanges while retaining recent exchanges verbatim, with boundaries that protect tool calls and results. The summary and retained starting point are written to the transcript; original history remains on disk. The current safeguard combines the existing summary, new messages, and recent progress to update old conclusions, avoiding continued use of corrected information as current judgment. [Reference 1](https://docs.openclaw.ai/concepts/compaction), [Reference 2](https://docs.openclaw.ai/reference/session-management-compaction/compaction).

Before formal compaction, a silent memory flush can let the Agent save important content using the selected memory provider’s tools. It serves a different purpose from a continuity summary: one preserves long-term information, the other reduces the working window. The documented default prompts for a flush 4,000 tokens before the formal compaction threshold and deduplicates it per compaction cycle. A save failure does not automatically clear the original session. [Reference](https://docs.openclaw.ai/reference/session-management-compaction/housekeeping).

OpenClaw also distinguishes lightweight tool-result pruning from semantic compaction. Client-side pruning considers cache TTL and context pressure and keeps the projection stable across subsequent requests; original tool results remain in the transcript. This does not imply all model services should use the same TTL or pruning threshold. [Reference](https://docs.openclaw.ai/concepts/session-pruning).

Failure handling has explicit trade-offs: general failures to produce a valid summary preserve the original history; automatic summarization timeouts have a separate degraded path that retains recent messages and the previous summary while noting omitted older messages. The latter can lose unsummarized details. A project prioritizing subject continuity may choose not to use that path. Safeguard checks for structure, unfinished requests, and identifiers do not guarantee semantic correctness of the summary. [Reference](https://docs.openclaw.ai/concepts/compaction).

## Letta: distinguish the hosted API design from the open-source local implementation

The official Letta V1 SDK documentation describes four modes: `sliding_window` retains recent messages and summarizes older ones in a separate call; `all` summarizes all history; the two `self_compact_*` modes retain the original Agent system prompt and tool definitions and append compaction instructions to the existing context. The documented default starts by summarizing about 30% of messages and increases the removed share in roughly 10% increments as needed. This is a starting proportion of messages, not a fixed precise token ratio. [Reference](https://docs.letta.com/v1-sdk/messages/compaction).

`self_compact_*` aims to reuse the normal request’s prefix cache for summarization. The same documentation allows a different summary model, including a provider’s lightweight model by default. The same system prompt and tools alone therefore do not guarantee a cache hit: if adopting this design for caching, explicitly use compatible routing to the same model and provider and measure cache usage. This is an engineering inference from the caching objective and model configurability. [Reference](https://docs.letta.com/v1-sdk/messages/compaction#compaction-modes).

The open-source `letta-ai/letta-code` commit obtained was `9a6b55b48c62bbacde0fb6dafee5fd450ee7b41e`. Its **local backend accepts only `all` and `sliding_window`** and errors on other modes. The four hosted API modes cannot all be claimed as implemented in this local backend. [local-backend.ts](https://github.com/letta-ai/letta-code/blob/9a6b55b48c62bbacde0fb6dafee5fd450ee7b41e/src/backend/local/local-backend.ts#L139-L153).

### Token budgeting: server usage anchor plus incremental estimation

The local estimator explicitly ports Pi’s approach: find the latest valid model `usage`, use its context usage as an anchor, and add estimated tokens for later messages; without valid usage, estimate the entire current window. A compacted window cannot keep using the larger pre-compaction usage, so old anchors are excluded using the summary time boundary. Fallback text estimation is still roughly character count divided by four, with about 1,200 fixed tokens per image; **it does not use an exact model-matched tokenizer on every request**. [local-context-estimate.ts](https://github.com/letta-ai/letta-code/blob/9a6b55b48c62bbacde0fb6dafee5fd450ee7b41e/src/backend/local/local-context-estimate.ts).

### Summaries, recent exchanges, and failure handling

The local sliding window selects an old prefix and recent tail at available boundaries, avoiding removal of the last unfinished tool call. Its default summary prompt carries forward still-valid content from the old summary and preserves high-level goals, progress, and clues for looking up history: recursive summarization. It checks that compaction reduces at least the message count or estimated token count. [compaction.ts](https://github.com/letta-ai/letta-code/blob/9a6b55b48c62bbacde0fb6dafee5fd450ee7b41e/src/backend/local/compaction.ts#L62-L95), [Reference 2](https://github.com/letta-ai/letta-code/blob/9a6b55b48c62bbacde0fb6dafee5fd450ee7b41e/src/backend/local/compaction.ts#L102-L143), [Reference 3](https://github.com/letta-ai/letta-code/blob/9a6b55b48c62bbacde0fb6dafee5fd450ee7b41e/src/backend/local/compaction.ts#L625-L688).

Summary generation finishes before the new window is saved. If the summarizing model itself encounters context overflow, the local implementation progressively reduces the historical text sent for compaction and retries. This sacrifices detail and is not lossless. Other errors propagate. [Reference 1](https://github.com/letta-ai/letta-code/blob/9a6b55b48c62bbacde0fb6dafee5fd450ee7b41e/src/backend/local/compaction.ts#L544-L589), [Reference 2](https://github.com/letta-ai/letta-code/blob/9a6b55b48c62bbacde0fb6dafee5fd450ee7b41e/src/backend/local/local-backend.ts#L865-L915).

The new window consists of the summary plus retained messages. A compaction entry is appended to the disk transcript with the boundary of the first retained message; original experiences remain in the transcript rather than being physically replaced or deleted. The local store also has a path for reading full history from disk. [Reference 1](https://github.com/letta-ai/letta-code/blob/9a6b55b48c62bbacde0fb6dafee5fd450ee7b41e/src/backend/local/local-store.ts#L1160-L1224), [Reference 2](https://github.com/letta-ai/letta-code/blob/9a6b55b48c62bbacde0fb6dafee5fd450ee7b41e/src/backend/local/local-store.ts#L3000-L3030), [Reference 3](https://github.com/letta-ai/letta-code/blob/9a6b55b48c62bbacde0fb6dafee5fd450ee7b41e/src/backend/local/local-store.ts#L2123-L2155).

## DeepSeek: an official tokenizer is available, but the complete model input must be counted

The official token usage documentation provides an offline tokenizer and states that returned `usage` is authoritative for actual counts; image estimates based on dimensions may still differ. When reviewed, the download pointed to `deepseek_v4_tokenizer.zip`, containing `tokenizer.json`, `tokenizer_config.json`, and a Transformers demonstration. An offline token count for plain text is not equivalent to the complete request count including message templates, tool definitions, and images. [Reference 1](https://api-docs.deepseek.com/quick_start/token_usage/), [Reference 2](https://cdn.deepseek.com/api-docs/deepseek_v4_tokenizer.zip).

### A more complete first-party option: deepseek-recipe

DeepSeek’s official open-source `deepseek-recipe` provides a Rust library and Python bindings covering conversion from Chat Completions / Messages / Responses to a unified Conversation, V4/V4.1 prompt rendering, encoding with an attached tokenizer, and multimodal processing. The commit obtained was `935817c66f5d6e64838f419692545f06787e485f`. [Reference](https://github.com/deepseek-ai/deepseek-recipe/blob/935817c66f5d6e64838f419692545f06787e485f/README.md).

Its tokenizer documentation calls for a model-matched tokenizer, rendering with the production prompt template, and correct handling of special-token ranges. The full prompt token count is the number of encoded token IDs plus `image_token_adjustment` beyond image placeholders; the sum of input and output reserve must then be checked against the model window. Tokenizing only `JSON.stringify(messages)` or using another model’s tokenizer cannot be called exact. [Reference](https://github.com/deepseek-ai/deepseek-recipe/blob/935817c66f5d6e64838f419692545f06787e485f/docs/tokenizer.md).

The official library includes separate V4 and V4.1 tokenizers and documents their provenance, special image-token adjustments, and reference versions. This further shows that tokenizer, model template, and multimodal encoding must be selected together. [Reference 1](https://github.com/deepseek-ai/deepseek-recipe/blob/935817c66f5d6e64838f419692545f06787e485f/static/tokenizers/v4/README.md), [Reference 2](https://github.com/deepseek-ai/deepseek-recipe/blob/935817c66f5d6e64838f419692545f06787e485f/static/tokenizers/v41/README.md).

### Options for this project (engineering recommendations, not implemented at the time)

- **Lighter token budgeting**: configure limits, triggers, and reserves in tokens; use a valid API usage anchor plus estimates for new messages, fall back to conservative estimates on the first turn and after compaction, and record differences between estimated and actual usage. Pi / Letta’s local implementation is a useful reference, but this is estimation in token units, not exact tokenization per request.
- **More precise model-specific approach**: convert Pi’s final request to the official prompt encoding matching the model version, count with the DeepSeek tokenizer, and handle images. The official solution is Rust / Python, creating integration costs such as bindings or a local helper process for this TypeScript project; still check templates and multimodal handling against server usage.
- Either way, trigger compaction when complete input plus output reserve plus safety margin approaches the window, rather than comparing UTF-8 bytes directly with the model’s token window. Cached input tokens still consume context capacity and cannot be deducted from the capacity budget. [Reference 1](https://github.com/deepseek-ai/deepseek-recipe/blob/935817c66f5d6e64838f419692545f06787e485f/docs/tokenizer.md), [Reference 2](https://api-docs.deepseek.com/quick_start/token_usage/).

## Project implementation and open decisions at the time

At the time, local `src/context.ts` measured UTF-8 bytes of serialized messages and added a fixed 5,000 for images; `src/brain.ts` directly compared this with 70% of the model token window, then compacted at 85% toward roughly 60% with a small summary budget. The measurement included some metadata not submitted as model input and mixed units. A recent change fixed the placement of cross-turn prefixes and dynamic snapshots, but not these budgeting issues. [Reference 1](../../src/context.ts), [Reference 2](../../src/brain.ts).

The summary used a separate system instruction and serialized removed history as user text, so the request could not directly reuse the normal thinking request’s long prefix. The summary existed only in memory, and any `run()` error cleared old working history via `resetContext()`. This differs substantially from committing only after successful, validated summarization and retaining the old window on failure. [Reference](../../src/brain.ts).

The following were engineering recommendations, not implemented behavior:

1. Configure working capacity, output reserve, recent retention, summary limit, and memory-flush lead time consistently in tokens. Byte limits may remain as separate resource protection but must not stand in for model capacity.
2. Use either a usage anchor plus incremental estimates or a complete model-matched tokenizer checked against usage. Reestablish the measurement baseline on the first turn, after summary replacement, and after system/tool/model changes; cached reads still occupy context.
3. Trigger from the complete request and reserves, compact at a completed tool-batch boundary, and retain current unprocessed observations, latest continuing state, and sufficient recent verbatim content rather than any arbitrary two messages.
4. Before compaction, let the same Agent silently use memory and continuing-state tools such as `remember` to save experiences and understanding it considers important. This follows ADR-0006’s consolidation by the primary subject; no QQ messages are sent during this stage. [Reference](../adr/0006-experience-understanding-and-continuing-state.md).
5. Generate summaries either with a separate request (possibly a lightweight model) or self-compaction using the same model, route, and prefix with instructions appended. The latter aims to reduce prefill cost for summary generation; after the summary replaces history, the new window still needs a new long prefix cache, so hits are not guaranteed throughout.
6. Use summary fields suitable for a digital life: recent experiences and their times/people/social contexts, changes in relationship impressions and their evidence, open topics, unfinished matters, actual action outcomes, and retrievable sources. The continuing-state database remains authoritative for current activities, commitments, and wake-up arrangements; the summary cannot override it.
7. Persist original working messages and summary boundaries under existing retention rules for restart recovery and source lookup; do not store model chain of thought. On explicit forgetting, invalidate related summaries, windows, and indexes according to source dependencies so deleted content cannot reappear. [Reference 1](../adr/0004-persist-continuity-beyond-model-context.md), [Reference 2](../adr/0006-experience-understanding-and-continuing-state.md).
8. Validate that the summary is not truncated, key identifiers and necessary state are complete, and the window actually shrinks and meets budget before atomically committing it. Ordinary summary failures retain the old window with bounded retries; explicit forgetting still invalidates old content according to management state. Observability should report estimated and actual tokens, cache reads, compaction frequency, and cost.

Suggested combination: use OpenClaw-style reserves, silent memory consolidation, traceable sources, and retention on failure; if continuing with a fixed DeepSeek model and prioritizing cache use, add same-model self-compaction from Letta’s public design. Measurement precision, summary generation, and persistence policy can be decided separately without adopting an entire Agent framework.

## Additional review: DeepSeek Harness (DSH)

DSH here means DeepSeek Harness. The review used official `deepseek-ai/deepseek-harness` `master` commit `22ddee3792402c3e70ec5f86a63c3e3e895a2f60`; `compaction-basic` was version `0.2.1-rc.3`. It is a Cordis plugin-based Agent harness marked developer preview by its authors, not a hidden compaction mechanism in the DeepSeek model service. [Reference 1](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/README.md), [Reference 2](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/compaction/compaction-basic/package.json).

### Unified token meter: usage anchor, not an exact tokenizer

DSH uses one `tokenMeter` for pressure assessment, region selection, and comparisons before and after compaction. It uses server usage as an anchor only when the latest successful call’s canonical request envelope matches the current request and actual total usage is at least the corresponding full estimate; it then adjusts by the signed difference between estimated current and anchor surfaces. If the envelope differs because the model, provider, tools, or call configuration changed, it falls back to a complete current-request estimate. An old usage number cannot simply be reused. [Reference](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/llm/token-meter/src/index.ts#L130-L194).

Fallback text estimation is still roughly character count divided by four plus role/block overhead; tool definitions are included. Images may use request-image pricing declared by the model adapter; routes without it still use structural estimation. The source does not integrate the official DeepSeek tokenizer into this general meter. The README explicitly notes that fixed character density underestimates CJK and JSON schemas, and an exact tokenizer remains undecided. [Reference 1](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/llm/token-meter/src/estimate.ts), [Reference 2](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/llm/token-meter/README.md#known-limitations-and-deferred-work).

### Trigger budget and recent retention

For model window `W`, effective request output reserve `O`, and extra headroom `B`, the default pressure trigger is `floor(min(W × 0.8, W − O − B))`, with `B=65536` tokens by default. The default budget for retaining recent verbatim content is `floor((W−O) × 0.16)` and can be changed to an absolute `retainTokens`; the summary output limit defaults to the headroom. By default, pressure compaction gets at most one additional attempt and confirmed context overflow at most one recovery retry. These can be overridden per provider/model; small windows need lower headroom rather than a copied 65,536-token default. [Reference](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/compaction/compaction-basic/src/config.ts#L18-L239).

Normal compaction is awaited in the serialized `agent/pre-step`; model switching also validates current history against the target model window. It is an asynchronous API call awaited at the current Agent step boundary, not another background subject summarizing and rewriting the window concurrently. [Reference](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/compaction/compaction-basic/src/index.ts#L157-L202).

### Two stages: prune large tool results, then summarize semantically

Once pressure reaches the threshold, if `tool-result-pruner` is installed it first prunes oversized tool results without a model call and remeasures. If pressure is then below the threshold, no summary is generated. By default, text over 8,192 Unicode code points is reduced to the first 4,096 and last 1,024 with an explicit pruning marker; non-text block order and other tool-result fields are preserved. Original events remain in the log through appended replacement/source relationships. This reduces the tool-output view, not semantic understanding of an entire experience. [Reference 1](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/compaction/compaction-basic/src/index.ts#L315-L371), [Reference 2](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/compaction/compaction-tool-result-pruner/src/config.ts#L8-L20), [Reference 3](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/compaction/compaction-tool-result-pruner/src/index.ts#L86-L182).

If pressure remains, the oldest safe prefix is summarized while retaining leading system messages and a recent verbatim tail budgeted in tokens. The boundary moves forward until no unanswered tool call crosses it; it is not an arbitrary message-count cut. Tool pairing is determined from current surface order and recomputed after window replacement. [Reference 1](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/compaction/compaction-basic/src/region.ts#L108-L155), [Reference 2](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/compaction/compaction/src/tool-pairing.ts).

### Self-summarization and caching

The default summary call replays original system messages, the last routed request’s tool definitions, and the historical prefix to remove, appending a compaction instruction. It defaults to the most recently routed provider/model, though another summary model can be specified. This structure aims to reuse the provider’s warm identical prefix, with only the trailing instruction new; cache hits are not guaranteed when the model or adapter projection changes. The implementation also passes session ID and tool history rather than serializing old messages into a new system prompt. [Reference 1](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/compaction/compaction-basic/src/region.ts#L533-L563), [Reference 2](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/compaction/compaction-basic/src/summarizer.ts#L128-L193).

The default summary format targets coding assistants, with fields for the original request, technical concepts, files and code, fixes, pending tasks, current work, next steps, and key constraints. Old checkpoints are recursively merged and invalid facts removed. The result is framed as `<compacted-summary>`; only output text is accepted and returned tool calls are not executed. Empty summaries, truncation at the token limit, errors/cancellation, and image output fail. [Reference 1](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/compaction/compaction-basic/src/summarizer.ts#L24-L80), [Reference 2](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/compaction/compaction-basic/src/summarizer.ts#L200-L244).

### Precise persistence, commit, and failure boundaries

DSH first appends `compaction/start`, waits for the summary, revalidates the region and current generation, and requires the framed summary to be smaller than the replaced region. It then synchronously appends the summary record and replacement messages, followed by `compaction/end`. The summary record includes original region sequence numbers, source events, model, and usage; window replacement changes the log-derived surface without physically deleting the original journal. Replay can restore the same window. [Reference 1](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/compaction/compaction-basic/src/region.ts#L190-L263), [Reference 2](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/compaction/compaction-basic/src/region.ts#L394-L428), [Reference 3](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/compaction/compaction-basic/src/region.ts#L470-L520).

This does not mean every compaction-stage failure fully rolls back: previously persisted tool-result pruning, image processing, or successful compactions remain; commit/end write failures have separate error and locking semantics. Ordinary preventive compaction failure only warns and continues the current turn without resetting all history. Only an actual `CONTEXT_WINDOW_EXCEEDED` enters recovery, and a bounded retry requires evidence of an increased surface replacement generation. Cancellation takes priority; no progress does not cause repeated retries of identical input. [Reference 1](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/compaction/compaction-basic/src/index.ts#L157-L173), [Reference 2](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/compaction/compaction-basic/src/index.ts#L213-L257).

### Applicability to this project (recommendations, not implemented at the time)

DSH’s compaction strategy is not tied to a single DeepSeek model, but its implementation depends on Cordis services, the DSH Agent, session journal/surface, LLM adapter, and token meter. It is not a standalone summarizer that can be plugged directly into Pi. Its algorithms and invariants are useful references; installing the package directly would introduce or replace substantial runtime infrastructure. [Reference 1](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/compaction/compaction-basic/package.json), [Reference 2](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/compaction/compaction-basic/README.md#smallest-working-composition).

Most applicable to this digital life are complete token pressure and output headroom, pruning retrievable large tool results first, sufficient recent verbatim content, same-model same-prefix summaries, commit after generation and validation, retaining the window on failure, and overflow retries only after progress. The default engineering summary template should be replaced with people/social contexts/experiences, relationship understanding and sources, current topics, commitments, and actual action outcomes; summary content must not all be promoted unconditionally to verified fact. The same digital life still decides how to consolidate long-term memory during its primary thinking process; a window checkpoint must not automatically overwrite long-term understanding. This adaptation follows ADR-0006. [ADR-0006](../adr/0006-experience-understanding-and-continuing-state.md).

In the reviewed default `compaction-basic` path, the stages are metering, optional pruning, region selection, summarization, and commit. **There is no OpenClaw-style memory-flush stage in which the original Agent first calls long-term memory tools.** `sessions.flush()` in the source writes session records to disk and is not long-term memory consolidation. This conclusion is limited to the package’s default path and does not rule out other plugins adding consolidation. [Reference 1](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/compaction/compaction-basic/src/index.ts#L315-L371), [Reference 2](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/compaction/compaction-basic/src/index.ts#L400-L443).

`sourceEventSeqs` in compaction records and the old journal support provenance and replay, but the reviewed package does not implement this project’s source-cascade policy: explicit forgetting invalidates original evidence, derived understanding, summaries, indexes, and windows together. Persisting summaries alone does not establish the required deletion semantics. If continuing with Pi/SQLite, this project must implement them and test that old summaries and restart recovery do not reintroduce deleted content. [Reference 1](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/compaction/compaction-basic/src/region.ts#L470-L520), [Reference 2](../adr/0006-experience-understanding-and-continuing-state.md).

## Codex: distinguish framework scheduling from provider-native compaction

This Codex review relies on OpenAI’s official documentation actually consulted and does not claim a complete audit of the current client source. Configuration distinguishes `model_context_window` from the trigger threshold `model_auto_compact_token_limit` and supports a `compact_prompt` override. `model_auto_compact_token_limit_scope` distinguishes counting the whole context from only growth after a continued compacted-window prefix. These are configuration capabilities; field names do not establish that all providers, frontends, and versions use the same internal path. [Reference](https://learn.chatgpt.com/docs/config-file/config-reference).

The official prompting guide relates first-class compaction to model integration with the Responses API. The API also offers server-side threshold compaction and a separate `/responses/compact` call. The latter returns a canonical new window that may contain retained messages and an opaque `encrypted_content` compaction item. Callers should use the complete returned window as-is in later requests without pruning, parsing, or modifying the checkpoint. Input sent for compaction must first fit in the model window. [Reference 1](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide), [Reference 2](https://developers.openai.com/api/docs/guides/compaction).

Codex App Server exposes `thread/compact/start`, returning immediately and reporting progress through `contextCompaction` lifecycle events on the same thread. This suggests modeling starting and completing compaction separately; it does not mean this project should convert social group environments into separate threads. [Reference](https://learn.chatgpt.com/docs/app-server#trigger-thread-compaction).

**Applicability**: token-based thresholds, compaction headroom, and explicit start/completion events are worth considering. Native checkpoints are state specific to a model service: OpenAI-compatible DeepSeek APIs do not imply checkpoint compatibility, and this project’s current Pi tool loop has no integration that directly consumes such returned windows. Opaque checkpoints that must be passed as-is increase the cost of source-level forgetting and migration between providers. If adopted later, preserve their dependencies, invalidate the whole checkpoint when any related source is explicitly deleted, and rebuild from records allowed to remain. This is an engineering inference from the official opaque/as-is contract and this project’s deletion requirements, not a description of all Codex internal state.

## Claude Code: same-prefix summaries, fixed-context reinjection, and session recovery

This review uses Anthropic’s publicly available product documentation and public repository; it does not use reverse-engineered or leaked source. The official repository does not expose the entire compaction engine, so the behavior below is not a complete internal algorithm audit. [Reference 1](https://github.com/anthropics/claude-code), [Reference 2](https://github.com/anthropics/claude-code/blob/main/LICENSE.md).

### Measurement, thresholds, and caching

Current official documentation exposes `/autocompact`, `autoCompactWindow`, `--autocompact`, and environment-variable configuration. The product accepts a range of 100K–1M tokens, capped by the actual model window. Defaults vary by model and runtime and cannot generally be described as a fixed 95%. The reviewed material does not establish that the implementation always counts precisely with a matching tokenizer per request. [Reference](https://code.claude.com/docs/en/model-config#context-window-and-auto-compaction).

Official caching documentation confirms that a separate summary request repeats the session’s original system, tools, and history to be compacted, appending a summary instruction to reuse a warm cache. After compaction the conversation layer becomes a shorter summary and its cache must be rebuilt; fixed system and unchanged reloaded project context may still hit. This project’s then-current summary request JSON-serialized history and changed the system prompt, so it lacked that prefix reuse. [Reference](https://code.claude.com/docs/en/prompt-caching#compacting-the-conversation).

### What survives compaction

Claude Code separates fixed rules and long-term memory material from ordinary conversation. After compaction it reintroduces required context such as root `CLAUDE.md`, applicable rules, auto memory, and plans; ordinary hook-injected content is summarized like history. `SessionStart` with `source: compact` can supply material still needed after compaction. Auto memory is separately stored and is not equivalent to one session summary. [Reference 1](https://code.claude.com/docs/en/context-window#what-survives-compaction), [Reference 2](https://code.claude.com/docs/en/memory#auto-memory), [SessionStart](https://code.claude.com/docs/en/hooks#sessionstart).

Session transcripts are saved by default as project-scoped JSONL files. Resuming a compacted session uses the latest summary, unsummarized messages retained by compaction, and subsequent messages; it does not return all summarized old history to the model. Interrupted tools with unconfirmed outcomes are not automatically rerun by default; their actual effects still require checking. Internal file schemas can change and are not suitable as a stable API dependency for this project. [Reference 1](https://code.claude.com/docs/en/sessions#what-a-resumed-session-restores), [Reference 2](https://code.claude.com/docs/en/sessions#where-transcripts-are-stored).

### Extension points, failures, and provider API boundaries

`PreCompact` can block automatic or manual compaction, `PostCompact` can observe a completed summary but cannot rewrite it, and `SessionStart(compact)` can reinject context. If huge input causes the window to fill again shortly after compaction, the product stops repeated ineffective compaction and reports thrashing. These hooks do not establish a verified atomic rollback protocol for every generation and persistence failure. [Reference 1](https://code.claude.com/docs/en/hooks#precompact), [Reference 2](https://code.claude.com/docs/en/troubleshooting#auto-compaction-stops-with-a-thrashing-error).

Anthropic’s API compaction and context editing operate at another layer: the former generates a summary, while the latter can clear old tool results or thinking content. These are service-specific capabilities, not proof that Claude Code uses that path in every mode, nor direct equivalents of APIs available in DeepSeek. Client strategies can inform this project, but provider-specific control parameters require separate adaptation. [API compaction](https://platform.claude.com/docs/en/build-with-claude/compaction), [API context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing).

**Applicability**: same-prefix summaries, reinjection of fixed state, persisted summary boundaries, pre/post compaction lifecycle events, and prevention of futile repeated compaction are useful ideas without switching to Claude Code. The product’s 100K minimum and engineering-file reread rules should not be copied directly into a smaller working window and QQ social setting. This project still directly supplies core persona, current activities, commitments, wake-ups, and actual action outcomes; the digital life still consolidates long-term understanding from sources.

## Project recommendations after the additional comparison (not implemented at the time)

1. Continue using Pi Agent Core and SQLite and maintain our own context module under ADR-0009. Use DSH’s pressure pipeline, cache-friendly summary requests, and validated commit invariants as primary source references without directly adopting its Cordis/Session runtime. [ADR-0009](../adr/0009-embedded-pi-with-local-state-and-cli.md).
2. Measure in tokens using either a model-matched tokenizer or valid usage anchors plus incremental estimates, observing estimated and server-measured usage separately. Include system, tools, input, images, and output headroom; invalidate old anchors after compaction or model/request-header changes.
3. Under pressure, first prune large retrievable tool outputs. If semantic summarization remains necessary, have the same digital life save important experiences, understanding, and continuing state, then generate a summary with the same system/tools/history prefix and a trailing internal instruction. This retains OpenClaw’s long-term memory consolidation stage while borrowing prefix reuse from DSH and Claude Code.
4. Summaries change only working context. Retain recent complete exchanges, current unprocessed observations, social context, and sources; persist the new summary boundary and dependencies. Commit only after generation and budget validation; general failures do not clear the old window, and overflow retries are bounded and require actual reduction.
5. Replace the generic coding summary template with one for the digital life’s continuity of experiences and relationships. Requests from group members remain social material and do not become accepted commitments merely because of a “user task” field. Judgments, reports, fiction, and unknown action outcomes must retain their original status.
6. Keep existing project rules for source-level explicit forgetting, cross-context sharing boundaries, 90-day raw-event retention, and long-term retention of important sources. DSH log source pointers, Claude Code auto memory, and Codex model checkpoints cannot substitute for these rules. No operational policy is changed or added here; a user decision is pending.
