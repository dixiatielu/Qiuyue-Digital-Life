# A management page apart from the daemon

Plugin configuration and user code can now be reloaded through daemon control operations, as revised by [ADR-0021](0021-reload-scoped-plugins-between-thoughts.md). The page remains a separate process and never executes user plugins or writes the life database.

[ADR-0009](0009-embedded-pi-with-local-state-and-cli.md) made a local CLI the first management interface. By 2026-11-02 the operator's routine work had outgrown it: editing `config.json` and the persona file by hand, tuning the system prompt, switching models and endpoints, keeping credentials in `.env`, watching what the digital life is doing, and restarting the daemon only once a thought and a memory review were both finished, which took reading the `trace` table by hand. The operator also needed to see which edits would discard the working context, since its identity covers the instructions (persona included), the model configuration, the account, and the tool set.

The management page is therefore a second process, `webui`, beside the daemon rather than inside it. It stays up while the daemon restarts or fails, and it starts before the configuration is loaded, so it can repair a configuration that no longer loads. It reaches the daemon only through what already exists: the control socket for status, pause, the life switch, and memory correction and deletion ([ADR-0003](0003-separate-runtime-control-from-social-requests.md)), one shared live subscription for the timeline, and a read-only connection to the life database for development, memory versions, and whether a review or a call is under way. It never writes the database. Changes to the operator's files take effect when the daemon restarts, as before; the page does not reload configuration into a running daemon.

Every save of `config.json`, the persona file, the system prompt, or `.env` replaces the whole file, is refused if the file changed since the page read it (other sessions and hand edits share the checkout), and is first loaded the way the daemon loads it. The text before and after each save is kept under the page's data directory. Before a save, the page builds the tool set the new configuration would start with, offline, and compares its working-context identity with the one saved in the database, so it can say whether a restart continues the working context.

The built-in system prompt stays in the program. An operator's version is a separate file named by `systemPromptFile`, outside git, which must keep the persona placeholder and the current-context boundary. The page keeps the built-in version it was written against and warns when the built-in one changes, since the operator's file does not follow it.

Model providers are the page's own list of endpoints. The daemon still reads only `config.json`; choosing a provider copies its address, API, key variable, and gateway options into the model, embedding, or drawing section, so a provider list cannot change a running life by itself.

The persona file stays the operator's, and the digital life's development stays its own ([ADR-0012](0012-self-maintained-development-alongside-the-operator-persona.md)): the page shows habits, practices, and impressions, and corrects or forgets them only through the same management commands as the CLI, which keep versions and sources.

The page listens on the loopback address by default and is reached through an SSH tunnel. It requires a token, accepts only loopback or the configured host name, takes writes only as JSON from its own origin, and never sends a credential's value back, only whether it is set and how it ends. When `webui.service` names the daemon's systemd user unit, it can start, stop, and restart the daemon, waiting by default until no thought or review is under way and giving up after fifteen minutes rather than cut one short.

Revision of 2026-11-03: credentials have their own file and reader. Saving `.env` through ordinary file history kept old secrets, and the general history endpoint could return them even though the credential list masked them. Credentials now have no value snapshots or history endpoint; their file retains only the name, time, and operation of the latest 100 changes. Existing secret snapshots are removed by the explicit migration command. `credentialsFile` defaults beside the configuration and may point outside the checkout. It is a plaintext file replaced atomically with mode 0600; new parent directories use 0700. Operating-system credential storage can be added later if needed.

Every consumer, including model connection tests and catalog models, uses the same reader: externally supplied environment variables, then the credential file, then legacy `.env`. Empty external values and null file entries explicitly disable a credential. File values are never exported to the process environment. Core consumers hold their startup snapshots; replacement plugin instances and each management request read a fresh one. The page shows sources and treats external values as read-only, and refuses credential saves based on an older file revision. Migration copies credentials before removing their legacy definitions, preserves newer file entries, and can be retried after interrupted cleanup. The original `apiKeyEnv`, `tokenEnv`, and `searchKeyEnv` names remain compatible. Ordinary interface language belongs in `config.json` as `uiLanguage`, with the earlier environment setting still accepted.
