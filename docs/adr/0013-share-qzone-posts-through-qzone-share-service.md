# Share Qzone posts through Qzone's share service

On 2026-10-29 the digital life told a friend it had sent one of its Qzone posts as a card, but nothing arrived. It had used SnowLuma's `send_tuwen_ark`, which sends OIDB 0xdc2_34 and reports success whenever the response envelope carries no error. The response body, which SnowLuma discards, carried 901501 "消息下发失败" ("rule type not match appid") for every card tried, whatever its link or text. No other SnowLuma interface produces the card QQ itself sends when a post is shared: an unsigned `share` segment arrives as "发送者版本过低，无法展示内容", and a mini-app card from `get_mini_app_ark` presents the post as Bilibili.

Qzone's web page shares a post by asking `trpc.qq.share.Service/CreateShare` (OIDB 0x9409_1) for a card signed for that post, using the share resource each post carries; QQ then sends the card as a json segment. Sent through SnowLuma, that card arrives exactly as a person's own share does, with a message receipt.

The digital life therefore has one tool outside the SnowLuma catalog, `share_qzone_feed`. This departs from [ADR-0010](0010-expose-native-snowluma-actions.md), under which it acts only through SnowLuma's native interfaces. The tool calls Qzone's web gateway, the one SnowLuma itself uses for recommended posts, with the account's Qzone cookies from SnowLuma's `get_cookies`, and sends the card through `send_private_msg` or `send_group_msg`. It is offered only while those interfaces are enabled, so the operator's permissions still govern it. It is recorded and deduplicated as one action by its target and post, following [ADR-0008](0008-preserve-unknown-action-outcomes.md): a failure before the card is sent is definite, and an unconfirmed send is not repeated. A recommended post is taken from the result that listed it. The digital life's own posts are read from its Qzone main page as the web page reads them, because the older interfaces SnowLuma reads them through lack the share resource. Friends' posts are not supported: reading a friend's main page this way was refused.

Anyone holding a shared card can open the post without logging in, and Qzone's web page warns that this holds even when the space is restricted. A recommended post's card also carries its author's QQ number. Whether a post may be shared into a setting is therefore a question of its [social context](../../GLOSSARY.md), and the tool's description says so.

The tool should give way to a native interface if SnowLuma adds one for Qzone's share service.

Revision of 2026-11-02: SnowLuma 2.3.4 added `get_qzone_share_ark`, which asks Qzone's share service for a card with the same request the tool made. On 2026-11-02 the cards it built for one of the digital life's own posts and for a recommended post matched the tool's in every field but the per-share time, token, and share tag. One such card sent to a friend returned a receipt and read back unchanged. The tool now builds its cards through that interface and no longer calls Qzone's web gateway or reads the account's cookies. It reads the digital life's own posts with `get_qzone_feed_detail`, and it is offered while `get_qzone_share_ark` and a send interface are enabled. The tool stays rather than giving way, because using the native interfaces directly would have the digital life copy the whole post into `get_qzone_share_ark`, then copy the signed card verbatim into a message. A post read that day ran to about 8,000 characters for its own post and 6,000 to 56,000 for recommended ones, and tool results longer than 12,000 characters reach it truncated. A card ran to about 1,800 characters of links and a signature. The tool takes the post by reference, and the card never passes through the model. SnowLuma refuses posts that Qzone marks as not shareable. When Qzone would warn a person before sharing, as it does for the digital life's restricted space, its notice is returned with the result. `get_qzone_home_feeds` now reads a friend's main page too, so a friend's post can be shared from the result that listed it, subject to the same question of social context.
