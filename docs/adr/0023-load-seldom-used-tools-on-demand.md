# Load seldom-used tools on demand where the model's API can

[ADR-0010](0010-expose-native-snowluma-actions.md) and [ADR-0022](0022-expose-complete-native-tools-through-platform-adapters.md) give the model every enabled native operation with its complete parameters in every call, and each adapter adds a whole catalog. On 2026-11-23 the working context declared 245 tools in about 116,000 characters, measured at 32,400 tokens by gemini-4-hydrogen. In the 30 days before, the 194 SnowLuma operations outside the plugin's `common` set together took 232 of 4,232 native calls, and 163 of them were not called at all. Over the last 7 of those days there were 4,331 model calls averaging 242,000 prompt tokens.

A plugin now marks a tool it expects to be used seldom. Under a model that can take a tool partway through a conversation, a marked tool is deferred: the instructions list it by name and what it does, and its declaration is left out until the model asks for it with `find_tools`. It is then declared from the model's next step and stays declared until the working context starts afresh; nothing is unloaded, since 31 different deferred operations were used in those 30 days. A call to a deferred tool that has not been loaded fails as not found, and loads it for the step after. Under any other model every tool is declared from the start, as before. A deferred tool keeps its original name and complete parameters, and passes the same permission checks, action ledger, and outcome rules ([ADR-0008](0008-preserve-unknown-action-outcomes.md)). Deferral is not a permission: the operator's allow and deny rules alone decide what is enabled ([ADR-0003](0003-separate-runtime-control-from-social-requests.md)), and loading a tool neither unlocks anything nor records an action. What this revises in ADR-0010 and ADR-0022 is only that every call carries every parameter schema.

SnowLuma defers the operations outside `common`. An external adapter defers nothing unless it names its `frequent` operations, and then defers the rest. A tool the system instructions name, as they do each activity's tools, is never deferred, because a model told of a tool by name calls it without asking for it first. With the example configuration 60 of 231 tools are declared and 171 listed; gemini-4-hydrogen measured the tools at 26,800 tokens declared in full and 13,400 this way, list included.

What is loaded is what the working context declares. The thinking process declares its loaded tools with each turn, Pi writes a change in them into the transcript as a system message, and replaying the transcript gives the tool set ([ADR-0004](0004-persist-continuity-beyond-model-context.md)). So a restored context has loaded what it declares, a rolled-back thought loses what it loaded, compaction folds the additions into the leading message, and the main process and a review each load their own. The context's identity covers every enabled tool and the list in the instructions, not what happens to be loaded.

`find_tools` takes names and answers with each tool's description and its plugin's documentation: results, examples, constraints, and parameter prose a declaration leaves out. It replaces `search_snowluma_tools`, `load_snowluma_tools`, and each adapter's `describe_api`, which described tools without loading any and were not called once in 3,349 tool calls over 14 days. Under a model that defers nothing it is still there for the documentation.

Whether a model can take a tool mid-conversation is read from its API. Pi's transports render the transcript's additions themselves where a model's compat flags say it accepts them: `tool_addition` blocks for Anthropic Messages, `additional_tools` items for OpenAI Responses, and later tool messages for Chat Completions. Its catalog sets the flags for capable models and an operator sets them for a custom one. Run through the operator's gateway on 2026-11-23 with the flags set, gpt-5.4-mini and gpt-6-luna called a tool added this way; claude-haiku-4-5 and claude-sonnet-5 accepted the request but did not see the tool: Pi sent the `tool_addition` block, and a definition of about 700 tokens raised the reported input by 22, so that route drops it before the model. The flags are therefore for a route where this has been checked. Gemini's `generateContent` takes a new tool only by replacing the request's tool list, and with it the cached prefix of the whole context, so there every tool is declared from the start.

Gemini's Interactions API can do it, and Pi 1.6.0 has no transport for that API, so the program carries its own (`google-interactions`). Requests are stateless: each replays the steps the API returned, and a thought, which has no place in Pi's message content, is carried whole in a thinking block. Thinking blocks stay in the running process and are left out of the saved context, as they already were; within the current turn the API takes back only the exact steps it sent, and in earlier turns a call may stand without its thoughts. `find_tools` is declared as the API's client-side tool search, whose result may carry declarations: the tools a transcript adds join the `find_tools` result before them, and one with no such result joins the request's tool list. Against gemini-4-hydrogen the request's tool list stayed byte for byte the same through a load, a later thought that reused the tool, and a restart, and the first request after the restart read 15,352 of 19,072 prompt tokens from cache; the shape compaction leaves, with the tool in the rebuilt list, was accepted too. These models cannot turn thinking off, and gemini-4-hydrogen refuses the `minimal` level, so a request that asks for no thinking, as a summary does, asks for `low`.

The API's server-side tool retrieval was built first and replaced. There the request declares every tool with `defer_loading` and the API searches for the model. Each search reads the whole prompt again, billed at the input rate, which at the working context's size costs more than several hundred calls save. With 194 functions deferred the model's first search came back empty in 49 of 60 requests, because the API lists a function under a namespace and finds nothing for a name asked for without it; one sentence in the instructions repaired that. A call to a deferred function is refused unless the search that loaded it is still in the history, which Google's documentation leaves unaddressed for a history that is summarized or cut. And it would have been one API's mechanism, where loading through the transcript is the same for every model that can take it.

Also considered and set aside: a single dispatching tool that calls operations by name, which would hide the tool name from the hooks that end a thought, find a call's chat, decorate a tool, and deduplicate an action.

Revision of 2026-11-25: thinking blocks no longer stay in the running process past their turn. Replies before the newest observation keep only their calls, and every reply does once its thought ends ([ADR-0024](0024-keep-what-happened-in-the-working-context.md)), so a running context holds no more of a reply than a restored one. Within the current turn the API still gets back exactly the steps it sent.
